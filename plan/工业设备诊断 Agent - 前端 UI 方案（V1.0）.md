## 一、方案总览

### 1.1 适用场景

| 场景 | 描述 | 对 UI 的核心诉求 |
|---|---|---|
| **S1 值班监盘**（主场景，占屏时间最长） | 工程师在办公位/中控室盯守告警流，被动接收告警并跟进诊断结论 | **一眼可扫**：新告警不丢失、进行中诊断可追、异常态（降级/超时）必须刺眼 |
| **S2 诊断跟进** | 告警触发后查看 Agent 的推理过程、追问细节、确认结论 | **过程透明**：工具调用、证据来源、置信度构成全可见 |
| **S3 报告审核**（高风险强制） | 审核员在 4h 时限内完成通过/驳回，需核对每条结论的出处 | **证据可核**：结论 ↔ 引用 ↔ 原文 逐层可下钻，无死角 |
| **S4 知识库运维** | 知识库管理员上传文档 → 准入审核 → 建库 → 对账 | **状态可见**：三存储一致性、失败重试、版本留痕 |
| **S5 图谱探索** | 从报告或手动检索出发，沿关系路径自查故障链 | **可探索**：路径置信度、跳数控制、节点关联文档 |
| **S6 评审/演示** | 向评审或客户做端到端演示（Phase 6 交付） | **可讲述**：一条主线从告警到报告的全过程可被逐步展开 |
| **S7 现场巡检**（轻量，受限） | 平板/手机端查看告警与报告只读内容 | **降级可用**：不做完整功能（对齐 §10.3「移动端不做」的边界） |

### 1.2 目标用户与角色化差异

沿用 §7.2 RBAC 的四角色，**UI 以角色为第一维裁剪**（同一套数据，四种工作台）：

| 角色 | 高频任务 | 首页默认落地 | 可见导航 | UI 关键差异 |
|---|---|---|---|---|
| **工程师** | 看告警、发起/追问诊断、写知识库草稿 | 告警看板 | 看板 / 诊断 / 报告 / 知识库 / 图谱 | 有「发起诊断」入口；**审核按钮对其不可见**（职责分离） |
| **审核员** | 审报告、驳回意见、审批知识库准入 | **待办中心（待审核队列）** | 看板 / 报告 / 知识库 | 首页即待办；显示**审核倒计时**与并发锁提示 |
| **知识库管理员** | 文档准入、版本发布、对账处置 | 知识库 | 知识库 / 图谱 | 显示 `pending_review / indexed / failed` 与对账差异面板 |
| **系统管理员** | 用户与权限 | 审计日志 | 审计（+ 只读看板） | **不展示敏感原始数据**（设备参数原文做掩码） |

> **设计原则**：**能力按角色裁剪，而非按角色隐藏同一界面**。避免"按钮灰着但不告诉你为什么"的挫败感——不可用操作一律以「原因文案」替代（如"你不能审核自己提交的报告"）。

### 1.3 核心功能（UI 侧闭环清单）

对齐 §10.1 Must 链 13 项，UI 侧需支撑：

1. **告警实时到达与去重呈现**（Must 1、2）
2. **诊断过程实时可视化**（Must 3–6，节点流 + 工具调用）
3. **证据引用强制呈现**（Must 7，每条结论可点开出处）
4. **结构化报告展示 + 高风险人工审核**（Must 8、9）
5. **降级路径显式化**（Must 12，"初步判断"必须与正式报告**视觉上不可混淆**）
6. **知识库管理与一致性对账**（Phase 1 移交物的消费端）
7. **图谱可视化与下钻**（Should）
8. **对话式追问**（Should）

### 1.4 设计原则（四条）

| # | 原则 | 具体含义 |
|---|---|---|
| **P1** | **证据先于结论** | 任何结论在 UI 上必须**与引用同屏**或**一步可达**；不允许出现"孤立结论"。 |
| **P2** | **不可知必须可见** | 置信度、降级原因、数据缺失、云端升级、审核超时——**不确定性与异常态必须在界面上有位置**，而非藏在日志里。 |
| **P3** | **安全边界即交互边界** | 系统不"一键执行"，UI 也就**不提供任何执行类操作**；审核不能被绕过，去重不能被人为压制。 |
| **P4** | **过程即产品** | Agent 的推理过程本身是核心资产，UI 要把它做成**可讲述、可回放、可审计**的主视觉，而不是一个 loading 圈。 |

## 二、信息架构与导航

### 2.1 一级信息架构

```
云侧工业 IoT 诊断 Agent（Web）
├── 1. 告警看板 /alarms            ← 事件入口（Agent 的触发器）
│     └── 告警详情（抽屉）
├── 2. 诊断控制台 /diagnosis       ← 过程与对话
│     ├── 会话列表（thread 列表）
│     └── 单会话 = 对话流 + 推理轨迹
├── 3. 报告工作台 /reports         ← 结论与审核（一页承载"详情+审核"）
│     ├── 待办队列（审核员默认落地）
│     └── 报告详情（含内嵌审核操作区）
├── 4. 知识库 /knowledge           ← 离线知识构建流
│     ├── 文档列表 / 上传准入
│     ├── 文档详情（版本 / 分块预览）
│     └── 一致性与对账
├── 5. 图谱探索 /graph             ← 关系证据
│     ├── 图谱画布
│     └── 节点检查器
├── 6. 审计日志 /audit             ← 仅系统管理员
└── 全局层
      ├── 全局命令面板（⌘K / Ctrl+K）
      ├── 右侧上下文检查器（Inspector，跨页复用）
      ├── 实时事件层（Toast / 连接状态条）
      └── 角色门控层
```

### 2.2 导航设计决策

| 决策 | 理由 |
|---|---|
| **五页面压缩为「五导航项 + 全局检查器」** | 不新增页面，用**右栏检查器**承载"证据/节点/文档/实体"等跨页详情，避免"跳走再跳回"的上下文丢失。 |
| **审核不单独成页，内嵌于报告工作台** | 审核员必须**边看证据边决策**；独立审核页会制造"审核时看不到证据"的返工。 |
| **告警看板为默认首页（审核员除外）** | 对齐 §1.4 主演示场景：**告警是系统入口**，导航重心应反映这一点。 |
| **不设"设置"一级入口** | 当前无多租户、无模型微调（§10.3），配置项极少；配置收进用户菜单二级。 |

### 3.2 各区域职责

| 区域 | 职责 | 关键约束 |
|---|---|---|
| **① TopStatusBar** | 全局态：活跃诊断数、云端预算余量、数据源健康、未读告警（含**去重聚合数**）、角色身份 | **常驻不滚动**；健康类状态**只做指示灯**，点击才展开详情（避免噪声） |
| **② NavRail** | 五页面 + 审计；**徽标显示待办数**（待审核 / 待准入 / 未处理告警） | 可按角色过滤；可折叠为图标条 |
| **③ Workspace** | 路由出口，每页面统一遵循「工具条 → KPI 带 → 主内容」三段式 | 页面内**不重复**放全局状态 |
| **④ Inspector（上下文检查器）** | **跨页复用的右侧抽屉**：引用原文、图谱节点、文档分块、工具出入参 | 这是本方案的**结构级亮点**（见 §8.1）：任何"引用→原文"的跳转都在此完成，**不离开当前页** |
| **⑤ StatusBar** | 存储/推理的实时健康与延迟；本地/云端路径指示 | 直接对接 §12.5 可观测性数据；是**演示时的可信度锚点** |

### 3.3 页面统一三段式骨架

所有一级页面统一采用该结构，降低认知负担：

```
PageToolbar    ← 我是谁、看什么、怎么筛（左对齐客观动作，右对齐视图选项）
KpiStrip       ← 3–5 个关键指标卡（可折叠）
MainCanvas     ← 列表 / 画布 / 详情（虚拟滚动）
```

```
┌ 工具条 ──────────────────────────────────────────────────────────┐
│ [状态:全部▾][严重度▾][设备▾][时间范围▾]        [看板|时间线|分组] │
├ KPI 带 ───────────────────────────────────────────────────────────┤

├ 主内容：告警流（虚拟列表）────────────────────────────────────────┤
│ ⚠ 高 │ 3#离心泵 · 振动RMS │ 7.8 mm/s (阈值 4.5) │ 10:24:11      │
│     │ ×8 同类已合并（5min 窗口）  · 状态：诊断中 ▸ 检索知识库      │
│ ─────────────────────────────────────────────────────────────────│
│ ⚠ 中 │ 3#离心泵 · 轴承温度 │ 78.2 °C (阈值 70)  │ 10:23:40      │
│     │ 状态：已出报告 ▸ 置信度 0.81 · 风险 高 · 待审核 ⏱ 3h12m     │

└──────────────────────────────────────────────────────────────────┘
```

| 组件 | 说明 |
|---|---|
| `AlarmFilterBar` | 状态/严重度/设备/时间；**筛选条件写入 URL**（可分享、可回放） |
| `AlarmStatStrip` | KPI 卡，其中「**已去重合并**」为独立指标——直接把 §6.5 去重能力做成可见价值 |
| `AlarmStream` | 虚拟列表（告警持续到达，需控制 DOM） |

**关键交互**：新告警 → 列表顶部**插入 + 高亮脉冲 3s**（不弹全屏 Toast，避免打扰监盘）；点击状态胶囊 → **跳转诊断控制台并定位该 thread**。

### 4.2 P2 · 诊断控制台 `/diagnosis`

**目标**：把 Agent 的黑盒变成可追、可读、可回放的过程。

```
┌ 左：会话列表 ─┬─ 中：对话流 ────────────────────┬─ 右：推理轨迹 ──────┐
│ ● 3#泵振动异常 │  用户/AI 消息交替                 │  ▸ 告警解析  12ms  │
│   分析中 ▸     │                                  │  ▸ 传感器分析 3.1s │
│ ○ 2#空压机电流 │  ┌──────────────────────────┐    │     异常=是 · 斜率↑│
│   已完成 0.81  │  │ AI：初判为轴承磨损可能…   │    │  ▸ 知识检索 640ms  │
│ ○ 1#风机温度   │  │ · 结论①「润滑不足」[1][3] │    │     命中 5 条      │
│   降级        │  │ · 结论②「轴承磨损」[2]    │    │  ▸ 图谱推理 210ms  │
│                │  ├──────────────────────────┤    │     路径 2 条      │
│                │  │ 🛠 retrieve_knowledge     │    │  ▸ 历史工单 180ms  │
│                │  │    耗时 640ms · 命中 5    │    │  ▸ 诊断推理 1.4s   │
│                │  │    [展开入参/出参]        │    │  ▸ 报告生成 待审核 │
│                │  ├──────────────────────────┤    │                    │
│                │  │ ⚠ 本地置信度 0.61 < 0.75 │    │  置信度构成 ▓▓░░   │
│                │  │   已升级云端复核…         │    │  ────────────────  │
│                │  └──────────────────────────┘    │  证据 5 · 图谱 2   │
│                │  [追问输入框…]  [快捷意图▾]      │                    │
└────────────────┴──────────────────────────────────┴────────────────────┘
```

| 组件 | 说明 |
|---|---|
| `ThreadList` | 会话 = 一次诊断线程；显示状态胶囊（分析中/待审核/降级/完成） |
| `MessageList` | 消息类型：`UserMessage` / `AgentMessage` / `ToolCallCard` / `SystemNotice` |
| `AgentMessage` | Markdown 渲染 **+ 行内引用锚点 `[1]`**（点击 → Inspector 打开原文）；每条结论**强制携带锚点**，无锚点即渲染为「⚠ 无来源结论」（理论不可达，作为防御性设计） |
| `ToolCallCard` | 折叠态只显示「工具名 + 耗时 + 命中数/关键摘要」，展开显示入参/出参（对齐 §5.1 契约的 `{ok,data|error,elapsed_ms,trace_id}`） |
| `SystemNotice` | 系统级事件：云端升级、限流、降级、重试——**独立消息类型**而非普通文本 |
| `TracePanel` | **节点流时间轴**（亮点，见 §8.2）：节点名 / 耗时 / 产出摘要 / 状态 |
| `ConfidenceBreakdown (mini)` | 右侧显示四段贡献条 + 证据计数 |
| `Composer` | 追问输入 + 快捷意图（"只给我手册依据"/"对比历史工单"） |

**关键交互**：任何 `[n]` 引用、任何工具调用 → **都在右侧 Inspector 打开**，页面不跳转。

## 六、关键交互流程与状态变化

### 6.1 状态机总览

**A. 告警状态（Alarm）**

```
            ┌─ merged（5min 窗口内被合并）
new ────────┤
            └─ active ──► analyzing ──► diagnosed ──► reported ──► reviewing ──► published
                                                          │                       ▲
                                                          └──► degraded ──────────┘（人工确认后）
```

**B. 诊断线程状态（Thread）**（对齐 §5.3 DiagnosisState + §5.4 路由）

```
queued → running → ┬─ need_cloud（confidence<0.75 升级）→ running（云端返回）
                   ├─ retry（局部重试 <3）
                   ├─ need_human（risk=high，interrupt）
                   ├─ degraded（<0.50 或重试≥3）
                   └─ done
running/need_human/countdown ──► failed（不可恢复）
```

**C. 报告状态（Report）**

```
pending_review ──┬─► published（审核通过）
                 ├─► degraded（驳回→需补充；或 24h 超时自动降级）
                 └─► pending_review（4h 超时→转派备用审核人，状态不变）
```

**D. 审核锁状态（Lock）**

```
unlocked ──(审核人打开报告)──► locked_by_me ──► submitting ──► released
                └──(他人持有)──► locked_by_other（只读 + 显示持有人与剩余 30s）
```

### 6.2 流程 F1 · 告警 → 诊断 → 报告（自动主链路）

| 步 | 触发 | UI 变化 | 绑定事件/接口 |
|---|---|---|---|
| 1 | 告警引擎产生告警 | `AlarmStream` 顶部插入新 `AlarmCard`，脉冲高亮 3s；`AlarmBell` +1；同 5min 同类 → `DedupBadge` 计数 +1 而**不新增卡片** | `alarm:new` |
| 2 | 系统自动触发诊断 | `AlarmCard` 状态胶囊切 `analyzing`；`ActiveDiagnosisIndicator` +1；**若用户正在该设备详情页 → 直接打开 `TracePanel`** | `diagnosis:progress` |
| 3 | 各节点依次完成 | `TracePanel` 逐节点点亮；`SystemNotice` 在降级/升级时插入对话流 | `diagnosis:progress`（`node` 字段） |
| 4 | 置信度 < 0.75 | 对话流插入 `SystemNotice`「本地置信度 0.61 < 0.75，已升级云端复核」；`CloudBudgetGauge` 变化 | — |
| 5 | 诊断完成 | 状态胶囊切 `reported`；`ReportQueue` 待办 +1；**高风险**时审核员端弹**可停留 Toast** + 声音（可关） | `diagnosis:done` |
| 6 | 高风险强制审核 | 审核员端 `ReportHeader` 显示倒计时；提交者若为当前用户 → `ReviewActionBar` 显示「不能自审」 | `review:required` |
| 7 | 审核通过 | `ReviewActionBar` 收起 → 状态切 `published` → `AlarmCard` 状态同步终态 | `POST /api/reports/{id}/review` |

### 6.3 流程 F2 · 人工发起诊断 + 对话式追问

```
工程师在看板点击「手动诊断」 → 预填 device_id/metric/time_range
   → 跳转 /diagnosis?device=3#pump&auto=1（自动创建 thread）
   → 首轮：Agent 返回带引用结论（含 TracePanel）
   → 追问："这台泵的历史工单怎么说？"
        → chat:ask → 对话流插入 UserMessage → Agent 复用 thread 上下文
        → 若触发新工具调用 → 追加 ToolCallCard + TracePanel 新增节点
```

**要点**：追问**不新建 thread**（复用上下文）；每次追问产生的**新结论仍强制带引用**。

### 6.4 流程 F3 · 高风险审核（含超时与并发）

```
审核员打开报告
  ├─ 获取锁成功 → 显示「已锁定给我，剩余 30s 自动续期」
  ├─ 获取失败 → 只读态 + 「张工正在审核（锁剩余 12s）」
  └─ 核对阶段（关键）：
       点 [1] → Inspector 打开手册原文并高亮命中段
       点图谱路径 → Inspector 切「实体」页签，显示邻接与关联块
       悬挂鼠标到结论 → 浮层预览引用摘要（不打断）
  → 决策
       ├─ 通过 → [通过并发布] → ConfirmDialog → published
       └─ 驳回 → 必填意见（≥10 字）→ degraded → 回流工程师补充
  → 超时
       ├─ 4h 未审 → 系统自动转派备用审核人 + 顶部提示条
       └─ 24h 未审 → 自动降级「待人工确认」；报告页显著提示，流程不挂起
```

### 6.5 流程 F4 · 知识库准入（知识库管理员）

```
上传 → MetadataForm（型号/类型/来源分级）→ 提交准入
   → 状态 pending_review（工程师可写草稿，管理员审批）
   → 批准 → Outbox Worker：PG pending → Milvus 向量 + Neo4j 三元组
        ├─ 全成功 → indexed（DocTable 显示绿色状态）
        └─ 任一失败 → failed + 补偿队列（IngestionJobList 显示重试次数）
   → 每日对账 → ReconcilePanel 差异（>0 时顶栏健康灯降级）
```

### 6.6 交互约束表（UI 行为规则）

| 场景 | 规则 |
|---|---|
| **长任务反馈** | 诊断过程必须给**节点级**进度（≥6 个节点），不允许只给一根不确定进度条 |
| **乐观更新** | 仅用于"筛选项/视图切换/标记已读"等**可回滚且非关键**操作；审核、准入**一律不使用乐观更新** |
| **失败提示** | 统一 `{code,message,trace_id}` 映射为「人话 + 建议动作 + trace_id 可复制」三段式 |
| **断线** | `ConnectionBanner` 顶部常驻提示「实时连接已断开，正在重连（第 2 次）」；断线期间**禁用审核提交**（避免状态不一致） |
| **空态** | 每个列表/画布必须有空态，且空态要说明"为什么空"（如"当前无待审核报告，4h 内超时 0 条"） |
| **加载态** | 骨架屏优先；诊断类内容用"节点占位 + 动画"表达"正在推理" |
| **可回放** | 已完成 thread 的 `TracePanel` 保留历史耗时，可重新展开（演示价值，见 §8.2） |

## 七、响应式适配方案

### 7.1 断点定义

| 断点 | 宽度 | 目标设备 | 布局策略 |
|---|---|---|---|
| **XL（主工作位）** | ≥ 1600px | 中控室大屏 / 双屏工作站 | 三栏固定：NavRail 展开 + Workspace + **Inspector 常驻** |
| **L（默认笔记本）** | 1280–1600px | 项目主力开发/使用机 | 三栏：NavRail 展开 + Workspace + **Inspector 抽屉化**（点击才出） |
| **M** | 1024–1280px | 小笔记本 / 分屏 | NavRail **折叠为图标条**；Inspector 为覆盖式浮层 |
| **S（现场平板）** | 768–1024px | 巡检平板（横屏） | **单列流式**：底部 Tab 导航；TracePanel 自上而下堆叠；图谱画布全屏 |
| **XS（手机，受限）** | < 768px | 手机 | **仅 3 个能力**：① 告警列表只读 ② 报告只读（折叠态） ③ 审核通过/驳回 |

> **边界声明**：XS 不做完整功能，对齐 §10.3「移动端 **不做**」。XS 存在的唯一理由是**审核超时风险的对冲**（4h 内人不在工位时能应急处理）。这一点需在设计评审中显式确认，避免范围蔓延。

### 7.2 各页面响应式降级规则

| 页面 | XL / L | M | S | XS |
|---|---|---|---|---|
| P1 告警看板 | KPI 带 5 卡横排 | 5 卡 → 横向滚动 | KPI 折 2×2，卡片改紧凑行 | 仅列表（设备+指标+状态） |
| P2 诊断控制台 | 三栏（会话/对话/轨迹） | 两栏，轨迹并入对话流下方 | 单列：会话切换用顶部 Tab | 只读对话流 |
| P3 报告工作台 | 左队列 + 右详情（审阅模式） | 队列抽屉化 | 单列，操作栏**吸底** | 结论+风险+置信度+审核按钮 |
| P4 知识库 | 表 + 对账面板并置 | 表为主，对账折叠 | 表 → 卡片列表 | 不支持（仅提示"请用桌面端"） |
| P5 图谱 | 左控制 + 画布 + 右检查器 | 左控制折叠，检查器浮层 | 画布全屏 + 底部抽屉 | 不支持 |
| Inspector | 常驻第三栏 | 抽屉（宽度 420px） | 覆盖式（宽度 100%） | 全屏 Sheet |

### 7.3 响应式的三条技术纪律

1. **布局用 CSS Grid 容器查询（或 Tailwind `@container`）**，而非在一堆 `useMediaQuery` 里手写分支——避免"断点散落在业务组件里"。
2. **列表 → 卡片 → 紧凑行** 的转换由**同一数据源 + 三种展示组件**实现（`DocTable` / `DocCardList` / `DocCompactRow`），而非 CSS 强行压缩表格。
3. **工业场景首选横屏**：S 断点默认为横屏优化；竖屏时 P2/P3 允许横向滚动但**不重排**（巡检现场竖屏持握为主，重排会打乱肌肉记忆）。

## 八、亮点设计思路与实现价值

> 以下 5 项均**直接对应 V5.0 的某个关键机制**，不是装饰性设计。

### 亮点 1 · 表达式「证据链」（Evidence Spine）——引用不是附录，是主线

**做法**
- 结论 / 根因 / 建议三处的每个条目末尾渲染 `CitationAnchor`（`[1][2]`），锚点即入口；
- 点击锚点 → **右侧 Inspector 打开原文 + 高亮命中段**（不跳页、不丢失当前上下文）；
- Inspector 内可继续跳「图谱实体 / 传感器曲线 / 历史工单」，形成 **结论 → 证据 → 原始数据 → 关系网络** 的四级下钻；
- 报告中提供「**引用覆盖检查**」微组件：`结论 3 条 · 全部有出处 ✔ · 引用正确率抽检入口`。

**实现价值**
- **把 §7 第三道防线（引用强制，无来源不出结论）从后端约束变成可见的产品能力**——评审时这是最有说服力的一屏；
- 审核效率提升：审核员无需切页核对，**审核时间直接缩短**（对应 §11.1「引用正确率 ≥ 90%」的可操作性）；
- 技术上复用同一 `InspectorDrawer` + `EvidenceItem` 类型，**一次实现、四页受益**。

---

### 亮点 2 · 诊断「推理轨迹」（Trace Panel）——把 Agent 的过程变成可讲述的对象

**做法**
- 右侧固定 `TracePanel`：把 LangGraph 的 6 个节点渲染为**纵向时间轴**，每节点显示 `名称 / 耗时 / 产出摘要 / 状态`；
- 节点状态用统一 `state-*` 语义槽位（pending / running / success / degraded / failed / skipped）；
- 点击节点 → Inspector 显示该节点完整入参/出参（`retrieve_knowledge` 就展示 5 条命中及其 score）；
- **历史可回放**：完成的 thread 时间轴不消失，可反复展开——演示时可"倒带"讲解；
- 顶部聚合条：`总耗时 2.1s（P95 预算 3s）` + 本地/云端路径标识。

**实现价值**
- 直击方案 §9.2 判定的"**Agent 驱动而非检索驱动**"差异化定位——**用户看得见"Agent 自己决定调了哪些工具"**，这是与普通 RAG 问答最直观的分野；
- 把 `diagnosis:progress` 事件（§5.6）用到了极致：**一个已有接口撑起整个核心体验**；
- 调试与交付双用：开发期是排障工具，交付期是演示道具，**不产生额外工程量**。

---

### 亮点 3 · 「可解释置信度」组件——把魔法数字变成一屏讲清楚的机制

**做法**
- `ConfidenceBreakdown` 不使用单一百分比数字，而是**四段堆叠条**：检索 0.35 / 传感 0.20 / 图谱 0.15 / 自评 0.30，每段显示 `权重 × 得分`；
- 下方叠加**阈值标尺**：`0.50（降级线）` 与 `0.75（升级/审核线）` 两个刻度 + 当前值指针；
- 标尺上直接标注**后果**：<0.50「仅初步判断」/ 0.50–0.75「已升级云端复核」/ ≥0.75「本地命中，可出正式报告」；
- 每段可悬停展开"为什么是这个分"（如 `graph_support = 1.0`，因为找到了 `CAUSES` 路径）。

**实现价值**
- 把 §6.1 的复合公式 + 温度缩放校准结果**可视化**，直接消解 §9.2 判定的"0.75 是无依据魔法数字"这一**评审最容易被击中的硬伤**——UI 上它变成了有刻度的、可解释的机制；
- 用户（工程师）能理解"为什么这次让我等云端"或"为什么只给我初步判断"，**显著降低对系统的不信任**；
- 组件纯展示、纯输入 props，**零业务耦合，可独立开发**。

---

### 亮点 4 · Inspector 上下文检查器——"不离开当前页的深度下钻"

**做法**
- 一个**跨页复用的右侧抽屉**（`Sheet`），承载四类内容：引用原文 / 图谱实体 / 文档分块 / 工具出入参；
- 支持**栈式浏览**（点引用 → 看原文 → 点其中实体 → 看图谱 → 回到引用），带面包屑与返回；
- 宽度可拖拽；在 L 断点及以上默认不遮挡主内容（推动而非覆盖）。

**实现价值**
- 解决工业诊断场景最痛的问题：**审核/诊断时需要反复对照多份材料**；
- 把"五个页面"的信息密度提升为"五个页面 + 一个无限深度的检查器"，**避免为每种详情开新页面**（工程成本显著下降）；
- 与亮点 1、2 天然耦合：**一个基础组件同时支撑两大亮点**，是投入产出比最高的一项结构性设计。

---

### 亮点 5 · 「诚实降级」视觉语言（Degraded-first）——不确定性与异常态有独立表达

**做法**
- **降级态不复用正式报告容器**：`DegradedBanner` 置顶 + 报告正文改用差异化的版式（更弱的强调层级、显式"初步判断"水印式标注）；
- 统一"**不确定性表达矩阵**"：

| 情形 | 表达方式 | 禁止 |
|---|---|---|
| 低置信度降级 | 独立 `degraded` 容器 + 原因 + 建议动作 | 禁止仅用灰色小字提示 |
| 云端升级中 | `SystemNotice` 消息 + StatusBar 路径指示 | 禁止静默等待 |
| 图谱与文档冲突 | 图谱路径标「待确认线索」+ 文档为权威 | 禁止两条证据同等权重展示 |
| 审核超时（4h/24h） | 顶部提示条 + 倒计时 + 转派记录 | 禁止自动"通过" |
| 数据源降级（Milvus→pgvector 等 §3.5） | StatusBar 健康灯降级 + 报告页脚"当前检索后端"标注 | 禁止沿用原指标而不标注 |
| 云端预算熔断 | 顶栏预算灯转警告 + Toast 说明 | 禁止静默失败 |

**实现价值**
- 把 §3.5 降级映射表、§5.2 错误码、§6.4 审核生命周期、§7.1 预算熔断这些**后端"隐性风险"全部变成前端可感知状态**——这是评审中"工程成熟度"的直接证据；
- 安全性：杜绝"把降级结论当成正式结论使用"的误用风险（对齐 §7 第三道防线）；
- 该矩阵本身可作为**前端验收清单**逐项打勾。

> **备选亮点（可选实现，优先级低于以上 5 项）**：
> - **演示模式（Demo Mode）**：`/reports/{id}?demo=1` 一键进入"讲解态"——自动逐段展开证据链、节点流按时间轴回放，服务于 §1.4 主演示场景与 Phase 6 交付。
> - **告警去重可视化**：在 `AlarmCard` 上以"×8"展开 5min 窗口内的原始告警序列，直接展示 §6.5 去重能力的价值（也回应 §11.1「去重有效率」指标的呈现）。

## 九、与视觉主题层的衔接契约

> **本方案不定义任何色值、字体、圆角、阴影**。以下为**留给视觉主题层的槽位清单与接入规范**，主题层只需按槽位赋值即可整体换肤。

### 9.1 三层 Token 架构（强制）

```
L2 组件绑定层（Component Token）   例：<Card bg={surface-raised}>
        ▲ 只允许引用 L1
L1 语义槽位层（Semantic Token）    例：--surface-raised、--risk-high
        ▲ 由视觉主题层赋值（唯一赋值入口）
L0 基础尺度层（Primitive）         间距 / 字号 / 行高 / 圆角 / 层级 / 动效时长
```

**硬规则**
1. **L0 尺度参数不需要视觉主题层参与**，本方案已在 §9.4 给出建议档位（可直接采用）；
2. **L1 是主题层的唯一作业面**，全部以 CSS 变量承载（配合 Tailwind `theme.extend` 映射），**组件内禁止出现色值字面量**；
3. 主题层应提供 **两套完整赋值**（明亮 / 暗色，本交付以**明亮为默认**，暗色保留可切换；换肤仅切 `html[data-theme]`），并保证对比度满足 WCAG AA（正文 ≥ 4.5:1，大字 ≥ 3:1）。

### 9.2 L1 语义槽位清单（**主题层交付清单**）

#### A. 结构与表面

| 槽位 | 用途 | 备注 |
|---|---|---|
| `--surface-base` | 应用最底层背景 | |
| `--surface-raised` | 卡片/面板 | 需与 base 有可辨层级差 |
| `--surface-sunken` | 内嵌区域（代码/原始 payload/表格斑马） | |
| `--surface-overlay` | 抽屉/浮层/模态 | 需支持半透明 + 背景模糊 |
| `--surface-hover` / `--surface-selected` | 交互态 | |
| `--edge-subtle` / `--edge-strong` | 边框/分隔线两档 | |
| `--edge-focus` | 焦点环 | 必须对底色高对比（明 / 暗两套赋值均需满足） |

#### B. 文本与图标

| 槽位 | 用途 |
|---|---|
| `--text-primary` / `--text-secondary` / `--text-tertiary` | 三级文字层级 |
| `--text-inverse` | 反色（徽标/实心按钮上） |
| `--text-link` | 引用锚点、可点击实体 |

#### C. 品牌与强调

| 槽位 | 用途 |
|---|---|
| `--accent-primary` / `--accent-hover` / `--accent-subtle-surface` | 主操作与选中态 |
| `--accent-on-primary` | 主按钮上的文字色 |

#### D. 状态语义（**最关键的槽位组**）

| 槽位组 | 取值项 | 使用位置 |
|---|---|---|
| **风险等级** | `--risk-high` / `--risk-medium` / `--risk-low` + 各自的 `-surface` / `-text` / `-edge` | `RiskBadge`、`SeverityBar`、报告头部、KPI |
| **流程状态** | `--state-pending` / `-running` / `-success` / `-degraded` / `-failed` / `-skipped` | `StatusPill`、`NodeStep`、`TracePanel`、`DocRow` |
| **置信度分段** | `--confidence-seg-1` … `--confidence-seg-4` | `ConfidenceBreakdown` 四段堆叠（检索/传感/图谱/自评） |
| **置信度阈值** | `--threshold-line` / `--threshold-over` / `--threshold-under` | 阈值标尺（0.50 / 0.75） |
| **数据源健康** | `--health-ok` / `--health-degraded` / `--health-down` | `DataSourceHealthLamp`、StatusBar |
| **降级提示** | `--notice-warning-surface` / `-text` / `-edge` | `DegradedBanner`、`SystemNotice` |
| **引用锚点** | `--citation-idle` / `-hover` / `-active` | `CitationAnchor` |
| **图表专用** | `--chart-line` / `--chart-baseline-band` / `--chart-anomaly-point` / `--chart-grid` | `MiniTrend`、传感证据 |
| **图谱专用** | `--graph-node-{故障模式/部件/症状/位置/措施}` / `--graph-link-high` / `--graph-link-low` | `GraphCanvas`（六类关系 × 置信度分档） |

> **语义约束（重要）**：`--risk-*` 与 `--state-*` **必须可区分**——因为同一屏内可能同时出现"高风险（业务属性）"与"降级（系统状态）"，二者语义不同、颜色撞车会造成误读。主题层需在此处做明确的色相/明度区隔。

#### E. 动效

| 槽位 | 用途 | 建议 |
|---|---|---|
| `--motion-fast` / `--motion-base` / `--motion-slow` | 时长档位 | 120ms / 200ms / 320ms |
| `--motion-pulse-alarm` | 新告警高亮脉冲 | 1–3 次，**不循环**（长时间脉冲在监盘场景是干扰） |
| `--motion-node-flow` | 推理节点流转 | 呼吸/流动，避免旋转 loading |

### 9.3 主题层对接接口（工程实现）

```ts
// app/theme/theme.ts —— 主题层只改这个文件
export const theme = {
  semantic: {
    surface: { base: '…', raised: '…', sunken: '…', overlay: '…' },
    text:    { primary: '…', secondary: '…', tertiary: '…' },
    risk:    { high: '…', medium: '…', low: '…' },
    state:   { pending: '…', running: '…', success: '…', degraded: '…', failed: '…' },
    confidence: { seg1: '…', seg2: '…', seg3: '…', seg4: '…' },
    // …
  }
};
```

- 输出为 **CSS 变量（`:root` / `.dark` 承载暗色槽位、`[data-theme="light"]` 承载明色槽位）**，Tailwind 通过 `theme.colors` 映射命名（如 `bg-surface-raised`、`text-risk-high`）；
- **组件永不直接 import 色值**，只使用 Tailwind 语义类；
- 切换主题 = 切换 `data-theme` 属性，**无需改任何组件代码**。

### 9.4 L0 尺度参数建议（无需主题层参与，可直接落地）

| 类别 | 建议档位 |
|---|---|
| 间距 | 4 / 8 / 12 / 16 / 24 / 32 / 48（4px 基准） |
| 字号 | 12 / 13 / 14 / 16 / 20 / 24 / 32（正文 14，数据密集场景可用 13） |
| 行高 | 紧凑 1.4（表格）/ 常规 1.6（正文）/ 宽松 1.75（报告正文） |
| 圆角 | 4（小控件）/ 8（卡片）/ 12（面板）/ full（胶囊） |
| 层级 | 0 内容 / 10 吸顶工具条 / 20 浮层 / 30 抽屉 / 40 Toast / 50 模态 |
| 栅格 | 12 列，XL 最大内容宽 1600，左右留白 24 |

**数字密度声明**：本系统为**高信息密度**界面（工业监盘 + 报告审核），**默认紧凑档**，需在主题层评审时确认字号与行高的可读性平衡（尤其暗色 + 大字距屏）。

### 10.2 数据与状态管理分工

| 类别 | 方案 | 说明 |
|---|---|---|
| 服务端状态 | React Query（或 SWR） | 列表/详情/分页/缓存失效；**不放进全局 store** |
| 实时状态 | `SocketProvider` + 订阅 hook | 事件 → 定向 `queryClient.setQueryData` 局部更新，**避免整页刷新** |
| 全局 UI 状态 | Zustand | Inspector 栈、NavRail 折叠、主题、当前 thread、筛选草稿 |
| 表单状态 | react-hook-form + zod | 审核意见、准入元数据（复用后端 Pydantic 契约的 zod 镜像） |
| URL 状态 | searchParams | 筛选/分页/选中项 **一律进 URL**（可分享、可回放、支持浏览器后退） |

### 10.3 与后端契约的对接要点

| 契约 | UI 侧处理 |
|---|---|
| 统一响应 `{code,message,data,trace_id}` | 统一拦截器转 `Result<T>`；`trace_id` 展示在错误态并提供复制 |
| 错误码 `E_TIMEOUT / E_NOT_FOUND / E_INVALID_ARG / E_UPSTREAM / E_CONFLICT / E_PERMISSION` | 映射为**人话 + 建议动作**（`E_TIMEOUT`→"稍后重试，已自动重试 2 次"；`E_PERMISSION`→"你的角色无此权限，请联系审核员"） |
| Socket 事件 6 个 | 见附录 A；事件消费集中在 `lib/realtime/` |
| 超时约定（2s/3s/5s） | UI 超时略大于后端（+30%）后进入"仍在处理中"态，**不直接判失败** |
| 幂等（`idempotency_key`） | 审核提交按钮**提交后立即禁用** + 服务端幂等双保险 |

### 10.4 性能约束（对齐 §11.1 延迟指标）

| 项 | 手段 |
|---|---|
| 告警流高频写入 | 虚拟列表 + `requestIdleCallback` 批量合并 + 去重合并（**同 key 只更新节点**） |
| 图谱规模 | 默认渲染 ≤ 200 节点；超出时按 `confidence` 截断并提示"已隐藏 N 个低置信节点" |
| 首屏 | 路由级 code-split；`react-force-graph` 仅 P5 懒加载（体积大） |
| 流式 | 对话消息支持 SSE/分片追加（若后端提供），先渲染骨架再补全 |
| 埋点 | 前端记录 `diagnosis:done` 到渲染的耗时，用于对账端到端指标 |

## 十一、UI 层面的安全硬约束（设计禁忌）

> 与 §7 四道防线一一对应，**这些约束不是"体验取舍"，是不可协商的设计红线**。

| # | 禁忌 | 对应防线 | 理由 |
|---|---|---|---|
| 1 | **不提供任何"一键执行/自动维修/下发指令"按钮** | ③ | 系统定位为辅助诊断，永久 Won't（§10.3） |
| 2 | **不提供"跳过审核""直接发布"的捷径（含任何键盘快捷方式）** | ④ | 高风险 100% 覆盖（§11.1） |
| 3 | **不隐藏降级状态**：降级报告禁止与正式报告使用同一视觉容器 | ③ | 防止降级结论被误用 |
| 4 | **不展示"无来源的结论"**：无引用时渲染显式告警而非正常文本 | ③ | 引用强制 |
| 5 | **不允许提交者自行审核自己的报告**（按钮不可用 + 明确原因文案） | ④ | 职责分离（SoD） |
| 6 | **管理员视图对设备参数/工单原文做掩码** | ① | 最小权限 |
| 7 | **不允许通过 UI 覆盖系统自动去重的结果**（不可手动"取消合并"） | ① | 防止人为制造告警风暴 |
| 8 | **云端升级提示必须显式出现**（即使请求成功） | ①③ | 数据脱敏开关的知情权 |
| 9 | **审核超时不允许"自动通过"，只能自动降级为待人工确认** | ④ | §6.4 生命周期 |
| 10 | **审计日志页面无编辑/删除入口**（含批量操作） | ④ | 不可篡改 |
