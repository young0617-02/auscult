# V2 压力档（1万–3万–10万块延迟与内存实测）实施方案

## Context（为什么做）

V2 混合检索的**质量对标已闭环**（EXP-V2-BM25：sparse Milvus 0.92 / ParadeDB 0.90、hybrid 打平 0.91），但**压力档从未执行**，是 M0.3「条件 Pass」的剩余条件项。压力档只测**延迟与内存**（不做质量，报告 §六 纪律），用于回答"两 BM25 实现在 1万/3万/10万块中文语料下的 P95 延迟、常驻内存峰值、建库耗时"，并回流到 V4b 联合仲裁（先定内存档）。

**目标**：填 `reports/p0-report-v2-hybrid-retrieval.md` §六 三行表（1万/3万/10万 × Milvus/pgvector × P95/内存峰值/建库耗时），让 M0.3 由「条件」进阶为闭环节点，收敛 M0.6 依赖。

## 现状（已探查确认）

- `scripts/v2_pg_build.py` 可复用：建 `kb_chunks` 表 + 灌语料 + 建扩展；**但会 `DROP TABLE kb_chunks`**（含我已建的 bm25 索引），且 dsn 默认还是旧 5927、注释仍写"真 BM25 悬置"——须修正为 5433 与 K-V2-1 正解。
- `run_v2.py` 已内置 `PgvectorRetriever`（`--pg-sparse paradedb`，`|||` 算子已验证兼容）与 Milvus 集合构建（`kb_v1` 服务端 `FunctionType.BM25`）；`evaluate()` 已有 `latency_ms`/`p95_latency_ms` 计时逻辑，可复用为延迟采样。
- 压力档目标表（§六 L282-286）：规模 1万/3万/10万，横列 Milvus 查询 P95 / Milvus 内存峰值 / pgvector 查询 P95 / pgvector 内存峰值 / 建库耗时，全为【待 D5 实测】。
- 运行环境：`auscult-v2-milvus`(19531/9092)、`auscult-v2-pg`(5433, 库 auscult_v2, root/123456)；Docker 内存上限 ≈20GB；纯 CPU 路线（不占 GPU，R10）。
- **隔离原则**：压力档聚焦 BM25 稀疏，**不灌 dense embedding**（避免长时调用 Ollama bge-m3，也隔离稠密路线干扰）；pgvector `embedding` 列允许 NULL。

## 实施步骤

### 1. 新增语料合成器 `scripts/v2_synth_corpus.py`
基于 `corpus_100.jsonl` 的工业术语覆盖面，用模板/词典组合合成 `chunk_id=seg_<k>` 的中文语料，规模参数 `--n {10000,30000,100000}`，落盘到 `experiments/v2/raw/corpora_v2/corpus_{n}.jsonl`。保持字段结构（`chunk_id`/`text`/`category`）与 load_corpus 兼容。

> 复用 `run_v2.load_corpus`；合成文本近似工业场景，但**不做质量评测**（压力档不关心语义准确性），只保证文本多样性充分。

### 2. 建库（两对照侧并行可省略 embedding）
- **ParadeDB 侧**：扩展/新增 `scripts/v2_pg_build.py --corpus <规模语料> --dsn <5433>`：
  - 修 dsn 默认 5433；在 `CREATE TABLE` 后**追加 K-V2-1 正解 bm25 索引**（`USING bm25` + ngram）替代注释里的"悬置"；灌语料时 embedding 列填 `NULL`。
  - ⚠️ 该脚本 `DROP TABLE`，故先备份/记录当前 100 行 bm25 环境，压测后如需恢复再重建（供 EXP-V2-BM25 复现）。
- **Milvus 侧**：复用 `run_v2.py` Milvus rebuild，将 `docs` 换成大规模语料（只建 sparse/BM25 集合，不建 dense 字段）。

### 3. 新增压测脚本 `scripts/v2_load_test.py`
对每规模 × 两实现（milvus `sparse`、pgvector `--pg-sparse paradedb` sparse）：
- **延迟**：用固定 query 集（取 golden_set 子集，如 20 条）重复 N 次检索，统计 `P95 latency_ms`（复用 run_v2 计时口径）。
- **内存峰值**：采样 `docker stats` 对应容器（milvus / pg），记稳态峰值。
- **建库耗时**：记录步骤 2 建库 wall time。
- 输出落盘 `experiments/v2/raw/EXP-V2-LOAD/`（JSONL/CSV），供回填。

### 4. 回填文档与 M0.3 判定
- `reports/p0-report-v2-hybrid-retrieval.md` §六 三行表由【待 D5 实测】填实测值，状态改「✅ 已实测」；§〇 状态表、红线声明（压力档从"未执行"移除）、修订记录同步。
- `reports/p0-gate-review.md`、`reports/p0-summary-phase0-2026-09-30.md`：M0.3/V2「条件 Pass」理由更新（压力档已闭环 → 条件解除判定 M0.3 是否完整过闸）；修订记录追加。
- `docs/prj-ledger-version-lock.md` §二.2.8 若涉及索引/规模说明同步。
- 若实测暴露内存超标或异常，须显式标注并回流 V4b 仲裁决策，不静默通过。

## 验证

- 冒烟：`v2_synth_corpus.py --n 10000` 生成后 `load_corpus` 能读取、`len==10000`；`v2_pg_build.py` 建库后 `SELECT count(*) FROM kb_chunks` 与为 `n` 一致，且 `\di` 见 `kb_bm25` 索引；Milvus 集合行数一致。
- 压测：每规模跑完确认输出 `p95_latency_ms`、内存峰值、建库耗时三项非空且合理（P95 随规模单调或接近、内存峰值不超 Docker 上限）。
- 回填后 `grep` 确认 p0-report-v2-hybrid-retrieval/p0-gate-review/任务总结/prj-ledger-version-lock 无「暂缓/待 D5 补」压力档矛盾残留（历史修订快照除外）。

## 风险与约束

| 风险 | 处置 |
|---|---|
| `v2_pg_build.py` 的 `DROP TABLE` 冲掉 EXP-V2-BM25 bm25 环境 | 压测前记录当前状态，压测后如需恢复重建（bm25_init.sql 已幂等） |
| 10 万块建库/压测耗时较长 | 分规模逐步跑（1万→3万→10万），每档留痕；必要时后台运行 |
| 10 万行两实现内存超 Docker ≈20GB | 纯 BM25 稀疏按量级应可控；若超限如实标注并回流 V4b 仲裁，不降级数据 |
| 违反"不重写 P0 资产"硬约束 | 只新增合成/压测脚本与 bm25 索引，不改 Milvus 主路线与既有质量结论 |
| 压力档变相做质量评测 | 严守纪律：只报延迟/内存/建库耗时，不评 Recall（沿用 §六） |
