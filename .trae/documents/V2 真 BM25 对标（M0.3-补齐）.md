# V2 真 BM25 对标（M0.3 补齐）实施方案

## Context（为什么做）

V2 混合检索的稀疏对标此前因 ParadeDB `No key field defined` 长期悬置，pgvector 侧降级用 `tsvector`（非 BM25），对标仅代表「Milvus 原生 BM25 vs PostgreSQL tsvector」。`K-V2-1` 已于 2026-09-28 闭环真 BM25 可用，因此『Milvus BM25 vs ParadeDB 真 BM25』实现间对标被列为 **P1 专项**。用户决定现在启动该专项，以补齐 **M0.3** 的稀疏对标闭环，为 **M0.6** 门禁重评铺路。

**目标**：在既有 `golden_set_v1.jsonl`（50 条）上，测出 Milvus 原生 BM25（jieba）与 ParadeDB 真 BM25（ngram）的 `Recall@5`/MRR/P@5 对比，显式声明分词口径差异（不重写既有 V2 结论），并回填各报告 M0.3 状态。

## 现状（已探查确认）

- `scripts/run_v2.py` **已内置 ParadeDB 分支**：[PARADEDB_SQL](file:///d:/DSHproject/auscult/scripts/run_v2.py#L394-L399)（`WHERE text ||| %s ORDER BY paradedb.score(chunk_id) DESC`）+ `--pg-sparse paradedb` 参数 + `R-V2-3` 强制声明。
- PG 容器 `auscult-v2-pg`（paradedb 镜像，端口 **5433**，库 `auscult_v2`，root/123456）。
- PG `kb_chunks` 表已存在：`chunk_id text 主键`、`text text`、`embedding vector`，**恰好 100 行**（corpus 已灌入），**但仅有主键 `kb_chunks_pkey`，无 bm25 索引** → `|||` / `score()` 直接跑会失败，这是当前唯一阻塞。
- run_v2.py 的 pg 类**无建表/建索引逻辑**（`rebuild` 仅 Milvus 侧），PG 侧依赖外部预置。
- ParadeDB 正确建索引 SQL（ngram tokenizer）来自 [K-V2-1.md](file:///d:/DSHproject/auscult/experiments/v2/raw/K-V2-1.md#L49-L67)：`key_field='chunk_id'` + `tokenizer:{type:'ngram', min_gram:2, max_gram:3, prefix_only:false}`。

## 实施步骤

### 1. 新建幂等初始化脚本 `experiments/v2/raw/bm25_init.sql`
为 `kb_chunks` 建 bm25 索引（复用 K-V2-1 正解，`IF NOT EXISTS` 幂等，可复现）：

```sql
CREATE INDEX IF NOT EXISTS kb_bm25
  ON kb_chunks
  USING bm25 (chunk_id, text)
  WITH (
    key_field = 'chunk_id',
    text_fields = '{"text": {"type": "text", "tokenizer": {"type": "ngram", "min_gram": 2, "max_gram": 3, "prefix_only": false}}}'
  );
```

> 用 SQL 文件 + `Get-Content -Raw | docker exec -i psql` 执行，规避 PowerShell 对 JSON 双引号的转义破坏（沿用 K-V2-1 教训）。

### 2. 建立索引并冒烟验证
```powershell
Get-Content experiments\v2\raw\bm25_init.sql -Raw | docker exec -i auscult-v2-pg psql -U root -d auscult_v2
# 冒烟：确认 bm25 索引可检索中文
docker exec auscult-v2-pg psql -U root -d auscult_v2 -c "SELECT chunk_id, paradedb.score(chunk_id)::numeric(6,4) FROM kb_chunks WHERE text ||| '离心泵' ORDER BY paradedb.score(chunk_id) DESC LIMIT 5;"
```
> ⚠️ 若 `|||` 算子在此索引上报错（K-V2-1 冒烟用的是 `@@@`），则回退把 `run_v2.py` 的 `PARADEDB_SQL` 改用 `text @@@ %s`（对齐已验证正解），小改一处并记录。

### 3. 跑 Milvus vs ParadeDB 稀疏对标（复用现有 evaluate/CLI，不改主体）
```powershell
python scripts/run_v2.py --eval evals\golden_set_v1.jsonl `
  --routes milvus,pgvector --pg-sparse paradedb `
  --mode sparse,hybrid `
  --out-dir experiments\v2\raw\EXP-V2-BM25
```
- `sparse`：直接对比两实现 BM25；`hybrid`：补 pgvector-paradedb 的 RRF 混合，与既有 Milvus hybrid 对照。
- 产物：`EXP-V2-<route>-<mode>-paradedb` JSONL + 汇总 CSV，落盘 `experiments/v2/raw/EXP-V2-BM25/`。

### 4. 数据分析与口径声明
- 汇总 `Recall@5`/MRR/P@5：Milvus BM25（jieba 语义）vs ParadeDB BM25（ngram 子串）。
- **显式声明分词口径差异**：ngram(2,3) 做子串召回、jieba 做语义切分，两实现数值差异属口径所致，**不得据此改写既有 V2 结论/选型**（Milvus 仍为主路线）。
- 记录到对标实验文件（对照 `K-V2-1.md` 风格，登记 `EXP-V2-BM25`）。

### 5. 回填文档（M0.3 由「划 P1」→ 视结果闭环）
- `reports/p0-report-v2-hybrid-retrieval.md`：§四 新增真 BM25 行（标口径）、§二.4 K-V2-1 行「划P1」改「已对标」、§六/§七 同步。
- `reports/p0-gate-review.md`：§一/M0.3 行、§三 V2 处置记录更新；判定 `Recall@5` 对标数据。
- `reports/p0-summary-phase0-2026-09-30.md`：§六 第 3/5 条、U-07 状态、修订记录。
- `docs/prj-ledger-version-lock.md` §二.2.8：真 BM25 后「对标划 P1」→「已完成对标」。
- `experiments/v2/raw/K-V2-1.md` §五：勾选 P1 遗留项。
- 若对标判据含数值门槛，需先在报告中写下门限再判（对齐用户「先量化门限再结算」惯例）。

## 验证

- 冒烟：`||| '离心泵'` 能返回数个 chunk 且 score 递减（证明 bm25 索引 + 检索算子链路通）。
- 对标跑完：确认 `--out-dir` 下生成 `milvus-sparse`/`pgvector-sparse-paradedb`/`pgvector-hybrid-paradedb` 等结果文件，汇总指标合理。
- 回填后复核：`p0-report-v2-hybrid-retrieval` / `p0-gate-review` / `任务总结` / `prj-ledger-version-lock` 四处 M0.3 表述一致，无「划入 P1」残留自相矛盾。

## 风险与约束

| 风险 | 处置 |
|---|---|
| `|||` 与 ngram bm25 索引不兼容 | 回退 `PARADEDB_SQL` 用 `@@@`（K-V2-1 已验证正解），记录回退原因 |
| ngram 召回含子串噪声，数值低于 jieba | 属口径差异，显式声明，不改选型 |
| PG bm25 索引占用额外磁盘/内存 | kb_chunks 仅 100 行，量级可忽略 |
| 违反「不重写 P0 资产」硬约束 | 只新增 bm25 索引与对标结果，不改 Milvus 路线/已有结论 |
