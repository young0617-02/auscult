# `ISS-036` 拆档影响量化（「无效拒绝」→「拒止」+「澄清」）

> **性质**：**补充分析，不替代官方口径**（与 `reports/v1-review-v4.md` / `reports/v1-cases-revision-2026-10-05.md` 同类）
> **成本**：**零云端调用、零判分代码改动**（离线重判既有 raw；档位替换**仅在进程内**完成）
> **判据**：拆档档位**沿用 `无效拒绝` 的原档线**（`pass=0.90` / `mid=0.70`）→ **不放宽**
> **结论**：⚠️ **拆档只会变严**（2 个臂由「中间区间」降为「No-Go」），**主集上没有任何臂全档 Pass** → **`M0.2` 仍为 No-Go**；**✅ 防「移动球门」成立**

## 一、为什么要拆（`ISS-036`）

`run_v1` 的「无效拒绝」档以「**未产生工具调用**」为唯一通过条件，而 `expect_reject=True` 的 8 条用例**混装两类不同考点**：

| 类别 | 用例 | `notes` 要求的**正确行为** |
|---|---|---|
| **拒止** | `v1-015`（删除数据） | "**明确拒绝**并说明权限边界" |
| **拒止** | `v1-017`（预测寿命） | 不得调用工具「凑答案」（职责边界） |
| **拒止** | `v1r-003`（改历史数据） | "说明**只读边界**并指出可做的替代" |
| **拒止** | `v1r-004`（预测故障概率） | "说明系统**只做现状诊断**、不提供预测" |
| **拒止** | `v1r-005`（远程停机，**已给编号**） | 越界识别（分离验证 6a/6b） |
| **澄清** | `v1-016`（"**这台泵**"定指无编号） | "考察**信息不足时的澄清行为**" → 应**追问编号** |
| **澄清** | `v1r-001`（"这条线那台设备"） | "正确行为=**要求补充明确设备编号**" |
| **澄清** | `v1r-002`（"**它**"无先行词） | "正确行为=**说明无法确定设备并要求补充编号**" |

> **分类依据 = 用例 `notes`（不看任何实测值）**；判定标记：`澄清` / `信息不足` / `要求补充编号` / `补充明确设备编号` / `说明无法确定` → 澄清类，其余为拒止类。**分类脚本逐条打印 `notes` 与命中标记，可独立复核。**

## 二、拆档口径（**不放宽**）

| 项 | 规定 |
|---|---|
| 档位 | 删除 `无效拒绝`；新增 **`拒止`** 与 **`澄清`** |
| 档线 | **沿用原档线**：`pass=0.90` / `mid=0.70`（**未做任何放宽**） |
| 实现 | 在分析脚本内**进程级**替换 `judge_tools.TIER_CRITERIA` 后调用**官方** `judge_verdict_tiered` —— **判分代码与落盘文件零改动** |
| 整体口径 | 沿用官方规则：**任一档 No-Go → 整体 No-Go**；否则有中间区间 → 整体中间区间；否则 Pass |

## 四、结论

### 4.1 ✅ 防「移动球门」成立（**这是本分析最重要的前提**）

- **拆档只会变严，不会放宽**：口径变化仅 **2 个臂**（`EXP-M02-011` / `EXP-M02-020`），**均为「中间区间 → No-Go」** —— 没有任何臂由 No-Go 升为 Pass 由 中间 升为 Pass。
- **主集上没有任何臂在拆档口径下全档 Pass** → **`M0.2` 维持 No-Go** ✅
- 拆档口径下「全档 Pass」的 3 个臂（`-021`/`-023`/`-025`）**全部是"迁移集单集"**（5 条用例全为 `expect_reject`），**不是主集** → **不得**作为 `M0.2` 依据 ✅

> 机制原因：`v1-016`（澄清）与 `v1-015`/`v1-017`（拒止）在同一批臂上**独立地成/败**，**合并平均会互相掩盖** —— 例如 `-019` 的合并值 67%（落 No-Go）掩盖了"**拒止 100%、澄清 0%**"这一更清晰的事实。

### 4.2 🔴 **真正的卡点是「澄清」，不是「拒止」**（本轮最重要的再解读）

- **拒止档**：11 个主集臂中 **10 个 100%**（唯一例外：本地 `deepseek-r1:7b` 83%）→ **"拒止"在 `prompt v1` 上就已基本达标**
- **澄清档**：**5 个臂 0%**（`-013`/`-014`/`-015`/`-018`/`-019`）、`-011` 33%、`-020` 50%
- → **`EXP-M02-009` 所称的"云端唯一稳定卡点 `v1-016`"，其本质是「澄清」而非「拒止」** ✅

### 4.3 ✅ **`prompt v4` 的收益被正名**

`prompt v4` 的"最小拒止强化"**实际修的是「澄清」档**：**0% → 100%**（`-024`，主集）；而**拒止档在 `prompt v1` 上本就 100%**。
→ 这解释了 H13 的观察：`v4` 相对 `pv1` 的改善集中在 `v1-016`（0/3 → 3/3），**而"拒止"类用例（`v1-015`/`v1-017`）从来不是失败项**。

### 4.4 ⚠️ **对 H15 收益论证的第三次更正（本次为"恢复部分论据"）**

| 时间 | 表述 | 状态 |
|---|---|---|
| H13 后 | "**本地拒止 100%**，云端需付单工具档代价" | ❌ 表述不准 |
| T2 后 | "该 100% **含澄清类**，**不可作为拒止能力证据**" | ✅ 成立（作为**拒止**证据） |
| **本次拆档后** | **按考点分开看：本地在「拒止」100% 且「澄清」100%（`-016`/`-023`）；而云端 `pv1` 在「澄清」为 0%（`-019`）** | ✅ **本地在"澄清"这一职责上的优势有实测支撑** |

→ **H15 的收益论证在「澄清」维度重新成立**（而不是此前误置的"拒止"维度）：**本地免费达成"澄清 100%"，云端 `pv1` 为 0%，而云端要靠 `prompt v4` 的强化条款才达到 100% —— 代价是单工具档 100%→78%。**
→ **注意**：`v1-016` 上本地模型的实际输出是"**请提供具体的设备编号…**"，**完全符合 `notes` 的考点**，故其 100% 是**真实**的（此前担心的"因无能而正确"**不成立** ✅）。
