## 一、目的与门禁线

### 1.1 目的

1. **全组件运行态压测**：把所有组件同时跑起来，量出真实的资源峰值；
2. **校准分组策略与替代清单**：确定哪些组件能共存、哪些必须分批启动、哪些需要轻量替代；
3. **一次性仲裁组合方案**：给出最终可落地的组件组合与驻留策略。

### 1.2 门禁线（逐字采用上游计划）

| 判据 | 条件 |
|---|---|
| **Pass** | **峰值 ≤ 24GB 且 GPU 可直通** |
| **中间区间** | **超限 ≤10% → 分组启动** |
| **No-Go** | **严重超限 → 启用降级映射并调整 MVP** |

**门禁线算式（V4a 已锁定）**：

```
峰值 ≤ 物理内存 × 75% = 32GB × 75% = 24GB
```

| 参数 | 值 | 来源 |
|---|---|---|
| 物理内存 | 32GB（34359738368 bytes） | `env/hardware.json` 实测 |
| 门禁阈值 | **24GB** | 32GB × 75% |
| 当前 Docker 上限 | **≈20GB**（`docker info` MemTotal=20972691456 bytes） | `docker info` 实测（2026-09-24） |
| 余量 vs 门禁线 | **8.49GB** | `env/hardware.json.constraints_for_v4a` |

> 🔴 **判据成立条件**：24GB 门禁线的测量前提是 **Docker/WSL2 能提供到 24GB 以上的可用内存**。
> 实测当前 **≈20GB**，即容器可用内存已到设计值；**24GB 门禁线须按容器内口径评估**（20GB < 24GB，天然无法触及宿主线）——"峰值"测量须先在容器内聚合口径下定义。
> 因此：**T1.1 未落地 → 本判据不成立 → 本报告不得下任何放行结论。**

## 四、T8.1 启动矩阵（单启 → 组合启 → 全启）

> **目的**：记录**每步的资源增量**，用于定位"谁最吃内存"。
> **方法**：从空载开始，按序逐个/逐组拉起，每步等待稳态后采样。

### 4.1 矩阵设计

| 步骤 | 启动内容 | 分组意图 | 容器内存增量 | CPU 峰值增量 | 启动耗时增量 |
|---|---|---|---|---|---|
| S0 | **空载基线**（仅 Docker 引擎，无业务容器） | 基线 | 0（WSL2 空闲 956MiB） | — | — |
| S1 | 基础存储：Milvus + etcd + MinIO | 向量检索栈 | etcd 31.1 + minio 87.6 + milvus 151.2 = **269.9 MiB** | ~3.4% | ~2–3 min |
| S2 | S1 + PostgreSQL/pgvector | 对照检索路线 | postgres **65.25 MiB** | ~0.02% | ~30 s（PG18 布局修复后） |
| S3 | S1 + Neo4j | 图谱栈 | neo4j **871.1 MiB**（堆/页缓存 1g/512m） | ~0.97% | ~1 min |
| S4 | S3 + TDengine + taosAdapter | 时序栈 | tdengine **197.1 MiB** | ~1.41% | ~1 min |
| S5 | S4 + Redis | 状态栈 | redis **8.57 MiB** | ~0.13% | <10 s |
| S6 | S5 + Mosquitto | 消息栈 | mosquitto **4.11 MiB** | ~0.02% | <10 s |
| S7 | S6 + 应用后端 + 前端 | 应用层 | **无镜像 → 未测**（本阶段仅 Dockerfile.decoder） | — | — |
| **S8** | **S7 + 模型层**（7B / BGE-M3 / reranker 按需加载） | **全启** | 容器 ≈1.38GB + 模型显存 5.7–6.5GB | — | 冷加载 7B≈9s |

**实测观察**：内存增量最大 = **Neo4j（871.1 MiB）**，其次 **TDengine（197.1 MiB）**；WSL2 内容器合计 ≈1.38 GB，模型走 GPU（宿主 Host RAM 增量很小）。**容器本身不构成 24GB 压力**，压力主要来自宿主桌面基线 + 模型显存。

### 4.2 关键观察项（每步都要记）

| 观察项 | 为什么要看 |
|---|---|
| 内存增量最大的组件 | 决定谁需要被"按需加载"或替换 |
| 哪一步出现 OOM / 容器被杀 | 直接给出"必须分组"的边界 |
| 启动耗时最长的组件 | 影响开发迭代体验与冷启动策略 |
| 是否有组件启动失败（依赖未就绪） | 影响 compose 的 `depends_on` 与健康检查设计 |

**本表结论**：内存增量最大 = **Neo4j（871.1 MiB）**，其次 TDengine（197.1 MiB）；WSL2 内容器合计 ≈**1.38GB**，模型走 GPU（宿主 Host RAM 增量小）；**容器本身不构成 24GB 压力**，压力主要来自宿主桌面基线 + 模型显存。

## 七、T8.4 判据核算

### 7.1 口径定义（**必须先定义，再核算**）

> 🔴 **这是本报告最需要显式澄清的地方**：24GB 门禁线的"峰值"指什么？

| 口径 | 定义 | 上限来源 | 与 24GB 的关系 |
|---|---|---|---|
| **口径 A：容器内峰值** | 所有容器内存之和的峰值 | 受 Docker/WSL2 上限约束（当前 15.51GB，设计 20GB） | **上限 20GB < 24GB** → 该口径下 24GB 线**永远不可能触及**，即"必然 Pass"但无意义 |

## 八、T8.5 联合仲裁（顺序不可乱）

> **仲裁顺序（逐字采用上游计划，绝对不可调换）**：
>
> ## ① 先定内存档 → ② 再定向量库与图谱 → ③ 最后定 Broker 与 LLM 驻留

### 8.1 为什么顺序不能乱

| 步骤 | 内容 | 为什么必须在这个位置 |
|---|---|---|
| **① 内存档** | 确定实际可用内存总量与保留余量 | 它是**所有后续决策的约束边界**。若先选组件再算内存，必然要反复推翻 |
| **② 向量库与图谱** | 在内存档内决定 Milvus 还是 pgvector、Neo4j 是否常驻 | 这两者是**内存消耗大户**，必须在最紧的约束下先分配 |
| **③ Broker 与 LLM 驻留** | 最后决定 Mosquitto/EMQX 与哪些模型常驻 | 它们**弹性最大**（Broker 可换、模型可按需加载），放在最后才有调整空间 |

**反例（为什么不能乱）**：若先定 Broker（步骤③的内容）再算内存档，一旦 EMQX 比 Mosquitto 多吃几个 GB，内存档要重算 → 向量库选型要重选 → 全部返工。这正是风险 **R9（Broker 选型改内存预算）** 的产生机制。

### 8.2 仲裁表

| 步骤 | 决策项 | 依据 | 结论 |
|---|---|---|---|
| **① 内存档** | 可用内存总量 / 保留余量 / 是否分组启动 | T8.4 核算 + 口径 B：26.38GB 超 9.9% | **中间区间 → 需分组启动**；项目增量 ≈6.73GB 在预算内；分配余量保留给模型显存 |
| **② 向量库与图谱** | Milvus vs pgvector；Neo4j 常驻或按需 | V2 路线（Milvus 原生 BM25 可用）+ 内存档 | Milvus 主路线（≈151MiB）；**Neo4j（871MiB）为内存最大户 → 建议按需/分批** |
| **③ Broker 与 LLM 驻留** | Mosquitto vs EMQX；7B 常驻/BGE-M3/reranker 驻留策略 | V3 Broker（Mosquitto 已用）+ ①②剩余空间 | Mosquitto 极轻（4MiB）常驻；**双 7B 择一常驻、另 7B 按需**；BGE-M3 临界共存 |
