## 三、逐项判据的适用对象与口径（**只做澄清，不改判据数值**）

### 3.1 V1 —— 判据适用对象是**首次成功率**，不是重试后成功率

| 项 | 规定 |
|---|---|
| **主判据口径** | **按类型分档重校**（2026-09-28，见 §3.1.1）：各类型按其档线判定；整体 = 有数据类型的**最差档位**。单线判据（首次成功率 ≥90%）退化为整体下界口径 |
| **辅助指标** | 重试后成功率（≤3 次内全对）—— **仅作辅助报出，不得作为过闸依据** |
| 可解析率口径 | 剥离 `think` **之后**再判 JSON；剥离前的失败不计入可解析率，须单独统计为"think 污染率" |
| 拒绝率口径 | "应拒绝却调用"与"应调用却拒绝"**分开报**，不得合成一个数字 |
| 报告粒度 | 20 用例 × 3 次 = 60 次调用/模型，单次百分比粒度 1.67%；须同时给出分子/分母（如 17/20） |
| 云端 baseline | **仅作上界校准，不参与 Pass/No-Go 判定**（判据只针对本地模型） |
| **术语澄清（2026-10-06）** | 按 `ISS-036` 拆档，「无效拒绝」档已拆为 **`拒止`**（要求明确拒绝）与 **`澄清`**（要求追问/要求补充信息）。自本条起，历史记录中的"**拒止卡点**""**拒止行为专项**"等表述应读作"**澄清卡点**"（`v1-016` 的 `notes` 要求的是**补充设备编号**）—— **历史措辞不追溯改写**。离线量化见 `reports/p0-analysis-iss036-tier-split-2026-10-06.md` |
| 中间区间处置的扩展 | 上游判据为两步（约束解码 + few-shot）；`docs/p0-decision-model-role.md` §四 在此基础上补充了"Schema 简化"与决策树。**过闸判定以上游两步为准**，扩展步骤属加固手段 |

> 只报重试后成功率会掩盖首次可用性，进而高估落地质量 —— 该写法在报告中**不被接受**。

### 3.1.1 V1 —— 判据按类型分档（2026-09-28 重校）

> **重校依据**：`EXP-V1-003` 分层实测（多工具双模型 0.00）＋归一化 uplift=0（EXP-V1-NORM）＋云端上界 0.60（EXP-V1-002，且为裸跑下界）。
> **归因结论**（见 `reports/p0-report-v1-tool-call.md` §7.3）：V1 No-Go 是 "判据定得过高 + 用例口径不严 + 7B 多工具编排硬限" 三者叠加，非单纯"7B 不够硬"；云端 27B 亦仅 0.60、参数值正确率仅 0.5882，故一条 90% 线卡所有类型**定在了无人可达的高度**。

| 类型 | pass 线 | 中间区间 | No-Go → 处置 | 分档理由 |
|---|---|---|---|---|
| 单工具 | ≥85% | 70–85% | <70% → 云端工具调用转正 | 本地启动 0.33–0.39，经约束解码+few-shot 有上扬空间 |
| 参数校验 | ≥85% | 70–85% | <70% → 云端工具调用转正 | 本地启动 0.50–0.67 |
| 多轮 | ≥85% | 70–85% | <70% → 云端工具调用转正 | 本地启动 0.22–0.67 |
| 无效拒绝 | ≥90% | 70–90% | <70% → 云端工具调用转正 | 拒止强化后"该拒绝却调用"可工程归零，安全边界要求高线 |
| **多工具** | **≥70%** | **50–70%** | **<50% → 架构切分（交云端或拆单工具多轮）** | 7B 结构性硬限（EXP-V1-003 双模型 0.00，27B 亦无突破），单独设低线，**不与其他类型混线**；P6 拆步后判据对象改为**步骤链完整率**（见下） |

**整体合成规则**：整体 = 有数据类型的**最差档位**（任一 No-Go → 整体 No-Go；否则恰有中间区间 → 整体中间区间；否则 Pass），保证 M0.6 可判。多工具 No-Go 触发**架构切分**而非整线云端转正，因为单工具/参数校验等本地可达成类型仍应保留本地推理。

**判据适用对象**：以上各档的判据对象均为**首次成功率**（第 1 次即全对），重试后成功率仍仅作辅助。

**多工具档的步骤链口径（P6 拆步，2026-09-30 新增）**

> **背景**：EXP-V1-003/005/007 显示"单响应并发多工具"是跨模型硬限（本地 7B 双模型 0.00–0.20，云端 27B 亦仅 0.50）。按本档 No-Go 处置「拆单工具多轮」实施后，多工具用例改为**步骤链执行**，判据对象随之改变。

| 项 | 规定 |
|---|---|
| 用例标记 | `evals/v3_cases.jsonl` 中多工具 5 例置 `"execution_mode": "step_chain"`，其余为 `"single"` |
| 主判据 | **用例级首次通过率**（`judge_tools.aggregate` 的 `分层_类型.多工具`）：拆步架构下「全部期望步**按序命中且各步参数正确**」才记 success；缺步记 `FAIL_STEP_CHAIN`。与其他类型同口径（任务级），档线可直接比较 |
| 辅助指标 | **步骤链完整率** = `1c_多工具步骤链完整率`（通过步数 / 期望总步数）——**仅作诊断/部分进展观察，不作为档位判定依据** |
| 比较口径 | 每步只取该步**首个**工具调用；同一步多调记为「步骤不经济」（note，不判失败） |
| 档线 | 沿用本档 pass ≥70% / 中间 50–70% / No-Go <50%，**不因拆步而放宽** |
| 代价口径 | 拆步引入多步往返，**端到端 P95 必须单列**（`run_v1.py` 的`latency_ms` 按组累计），不得只报单步延迟 |
| 与 R-2/R-3 的关系 | 拆步为 P6 方案 B（本地保留），**实测负结果**（多工具档 qwen 20% / ds 0%）；再触发 P7 方案 A（交云端编排，EXP-M02-001）**多工具用例级亦仅 50%**（集合覆盖 1.00，编排本身无问题）→ **方案 A/B 均已试否**，失败共同收敛到**参数值语义**（云端参数值正确率 0.5882 与本地同源）→ 多工具档下一步转「**复审参数值判据/用例口径**」 |

**V1 判据/用例口径复审（F1–F6，2026-09-30 已执行）**

> **背景**：按上述「复审参数值判据/用例口径」专项，逐条复盘 `EXP-M02-001` 的 8 条失败（`reports/p0-review-v1-criteria-r3.md` §二），识别出 4 类根因：A 实现缺陷（假失败）/ B 任务信息不足（题目不可做）/ C 判据过严或用例歧义 / D 模型确实错。**只修 A–C 类，D 类（v1-016 幻觉设备号）不放宽；阈值不动、用例不删。**

| 修正项 | 对象 | 性质 | 落地形态 | 效果（已实测） |
|---|---|---|---|---|
| **F1** | `llm_adapter._normalize_structured_calls` | **生成侧**实现缺陷 | 兼容裸单对象工具调用（+`--selftest` 用例） | 消除 v1-001「假格式退化」；重判不可见，随 F2 重测体现 |
| **F4** | `judge_tools._query_semantic_match` | **判据侧**过严 | 增关键概念命中（域词表），bigram 交叠不足时按概念覆盖判等价 | 历史重判新增接受 52 处 / 去重 16 例；抽样复核 13 合规、2–3 观察、**无跨主题误接受**（风险低） |
| **F5** | 用例 v1-018（同类） | **用例侧**歧义 | 列入复核候选 → `lenient_param_defaults.aggregation` 允许多解（max / count_over_limit） | 按多解判对，逐条留痕 |
| **F6** | `judge_tools._refs_type_ok` | **判据侧**严于规格 | 对齐规格「**至少一条**」：`evidence_refs` 非空且 type ∈ 枚举即通过；覆盖度降为诊断项 | 历史重判 evidence_refs 类失败减少 |
| **F2** | `schemas/tools_v4.json`（+`prompts/tool_call_prompt_v3.md`） | **输入侧**任务信息不足 | 补 5 个规范测点目录 + 轴向/驱动端映射；**必须重测** | ⬇ 见下 |

### 3.1.2 V1 判据**适用对象** —— 按职责拆分（2026-10-07，处置 `ISS-035`）

**处置（经用户 2026-10-07 授权）：V1 分档按职责拆分「判据对象」——**

### 3.1.3 V1 判定口径 —— **同日多轮聚合**（2026-10-08，经用户授权）

> **依据**：`ISS-028` 实证**单日 `repeat=3` 点估计在云端即可跨档漂移**（`EXP-M02-038` vs `-039`，同日：单工具 83.3%↔88.9%、多工具 83.3%↔66.7%）→ **单日点估计不足以裁决 `M0.2`**。
> **口径**：`M0.2` 的 V1 判定采用「**同日多轮聚合**」—— 同配置、同日跑 **N 轮**独立端到端管线（`scripts/run_e2e.py`），用 `scripts/aggregate_runs.py` 把**逐样本**合并；各档率 = 合并通过数 / 合并样本数；**整体 = 最差档位**（`judge_verdict_tiered`）。
> **档线（不放宽）**：沿用 §3.1.1 原线（单工具/参数校验/多轮 ≥85%、多工具 ≥70%、拒止/澄清 ≥90%）。
> **纪律**：轮数**预登记**、**不提前停、不挑选轮次**；聚合口径与**单轮口径不可直接比较**。
> **实测（`EXP-M02-040`，3 轮同日，合并 225 样本）**：单工具 **92.6%**（50/54）、参数校验 **100%**（36/36）、多工具 **75.0%**（27/36）、多轮 **100%**（27/27）、拒止 **100%**（45/45）、澄清 **100%**（27/27）→ **整体 Pass**（合并首次成功率 **0.9422**）。
> **残余风险（必附）**：① 单轮口径下 R1 仍判**中间区间**；② **多工具档余量仅 5.0pp**（75.0% vs 70% 线）；③ 结论**依赖 provider 版本**（`ISS-028`，不可 digest 化）。

### 3.4 V4 —— 门禁线算式与口径

```
峰值 ≤ 物理内存 × 75% = 32GB × 75% = 24GB
```

| 项 | 规定 |
|---|---|
| 门禁阈值 | **24GB**（32GB × 75%）；基数取自 `env/hardware.json` 实测的物理内存 32GB |
| 中间区间 | 超限 **≤10%**（即 ≤ 24GB × 1.1 = **26.4GB**）→ 分组启动 |
| No-Go | 严重超限 → 启用降级映射并调整 MVP（须同步修订 `docs/p0-spec-scope-mvp.md`） |
| V4a（D1） | 采集物理约束，**预先裁定**轻量替代；判据 = 峰值 ≤ 物理内存 × 75% |
| V4b（D8） | 全组件运行态压测，**校准**分组策略与替代清单 |
| 判据成立前提 | 24GB 门禁线的测量前提是容器/WSL2 能提供到 24GB 以上的可用内存。实测当前 Docker 引擎上限 **≈20GB**（`T1.1（.wslconfig）`已安装核验 2026-09-24）。 |
| **口径（已裁决）** | ✅ **2026-09-24 裁决：采用口径 B（宿主总占用）**，因算式基数是"物理内存 × 75%"，只有宿主总占用与 24GB 直接可比。核算与实测见 `reports/p0-report-v4b-resources.md` §七（峰值 **26.38 GB / 31.80 GB**，超 9.9% ≤ 10% → **中间区间**），原始台账 `experiments/v4b/raw/EXP-V4B-T84-gate.md` |
| 口径差异说明 | `.wslconfig` 设计值 `memory=20GB` **小于**门禁线 24GB；若采用"容器内峰值"口径，24GB 这条线永远不可能触及、判定失去意义 —— 这正是选择口径 B 的理由 |

> V4 判据含两个分支："峰值 ≤ 24GB"与"GPU 可直通"。GPU 直通当前实测为 **UNVERIFIED**（本机仅有 `docker-desktop` 工具发行版，其内无 `nvidia-smi`），该分支同样无法判定。

### 3.7 R4 —— 判据按维度分档（2026-09-29 新增，P1 专项，ISS-014）

> **对象**：R-4「读证据→写根因/结论→带 `evidence_refs` 引用」的**本地**证据归纳/诊断（`reports/p0-gate-review.md` 登记 ISS-014）。**R-4 合规锁死本地**（云端仅传脱敏摘要与结构化参数、不传证据原文），无云端 baseline；**不落库、不转云**，只判模型产出的 `generate_report` 归纳结构是否结论正确 + 引用忠实。
> **主判据口径**：**首次成功率**（第 1 次即全维度通过）。各维度率分子/分母须分行报。判据对象与 V1 §3.1 一致（重试后成功率仅作辅助，不作为过闸依据）。

| 维度 | Pass 线 | 中间区间 | No-Go |
|---|---|---|---|
| 结构可解析率（合法 generate_report JSON） | ≥0.90 | 0.70–0.90 | <0.70 |
| **引用忠实（幻觉率）[红线]** | **幻觉率 = 0** | **0<幻觉率≤0.15** | **>0.15** |

| 根因结论正确率（`root_cause_keywords` 全含） | ≥0.70 | 0.50–0.70 | <0.50 |
| severity 匹配率 | ≥0.70 | 0.50–0.70 | <0.50 |
| 建议动作非空率 | ≥0.90 | 0.70–0.90 | <0.70 |

**整体合成**：整体 = 有数据维度的**最差档位**（任一 No-Go → 整体 No-Go；恰有中间区间 → 整体中间区间；否则 Pass），与 V1 §3.1.1 同构。幻觉维度计入整体（红线，权重最高）。

**No-Go 处置（合规锁死，禁止"转云传证据原文"）**：
1. **回灌闭环**：对引用幻觉/漏引用例启用 `--max-retry` 重试并复查幻觉率是否归零；
2. **提示词/few-shot 加固**：扩充 `prompts/r4_prompt_v1.md` 反例（引用包外 ref 的负样本），**新开 `experiment_id`** 复测；
3. **架构约束解码（加固路径，可选）**：动态 grammar 把 `evidence_refs[].ref` 约束为当前证据包 ref 集合（硬性阻断幻觉；依赖后续 `gbnf_grammar` 支持动态注入，**【待实测】**）；
4. **模型档位升级**：换更大的本地量化模型（如 13B Q4，受 V4 显存约束）。

**中间区间必留两行**：做了什么 + 代价（`Recall@5` 影响 **同 §3.5 无影响**（R-4 不改变检索层）；`P95` 影响【待实测】——重试次数上升会推高 P95）。

> **实测回填（2026-09-29，EXP-R4-001，81 响应）**：本档位已按初值实测并判分，**整体 Pass**。各维度率（分子/分母）：结构 78/81=**0.96**、引用忠实(幻觉) 81/81=**1.0**、幻觉率 **0.0**（红线=0 达标）、证据覆盖 78/81=**0.96**、根因 75/81=**0.93**、severity 72/81=**0.89**、建议动作非空 78/81=**0.96** —— **均达各自 Pass 线**；整体 = 最差维度 = **Pass**。辅助：首次成功率 0.741（不作为过闸依据）、平均延迟 3.96s / P95 5.08s。结论回填 ISS-014（已闭环）与 p0-decision-model-role §6.1 R-4。专项资产：`evals/r4_cases.jsonl`（20 条）/ `prompts/r4_prompt_v1.md` / `scripts/judge_r4.py` / `scripts/run_r4.py` / `experiments/r4/raw/EXP-R4-001.jsonl`。

## 五、降级代价标注纪律

> **铁律（上游计划 §一.4 第 3 条）：降级必带代价。** 任何轻量替代都须标注对 **`Recall@5`**、**`P95`** 的影响。
