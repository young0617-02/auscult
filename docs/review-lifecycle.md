## 一、设计目标

人工审核是"**高风险结论必须有人签字**"的强制关卡（V5.0 §十 Must #9：高风险命中 → 强制人工审核）。本策略保证：

| # | 目标 | 衡量方式 |
|---|---|---|
| 1 | 高风险 **100%** 进入审核 | 审核覆盖率 = 100%（审计日志核对） |
| 2 | 审核**不会因为技术原因丢失** | 无"审核白做"事件 |
| 3 | 审核流程**不会无限期挂起** | 超时必有确定动作 |
| 4 | 双审核人并发**不产生重复报告** | 重复报告数 = 0 |
| 5 | 审核**不依赖模型能力** | 触发条件为确定性规则（见 §二） |
| 6 | 全过程**可审计** | 每次状态变更留痕，不可篡改 |

## 二、审核节点触发条件（**确定性规则，刻意与 V1 解耦**）

### 2.1 为什么要与 V1 解耦

> **决策**：审核触发**不使用 LLM 判定**，只使用**确定性规则（关键词命中 + 阈值）**。

| 理由 | 说明 |
|---|---|
| **安全边界不依赖模型** | V5.0 §七 防线②明确："高风险判定**不依赖 LLM**"。若模型判断力不足（V1 结论可能是中间区间），安全关卡会失效 |
| **可单测** | 确定性规则可用单元测试穷举，LLM 判定无法穷举 |
| **与 V1 解耦** | **V5（checkpoint 验证）不等待 V1 结论**，可用硬编码关键词直接触发 `interrupt()`，让 D6–D7 的验证不被 D2–D3 结果阻塞（"机器并行、人串行"的落地方式） |
| **可解释** | 审核日志能明确写出"因命中关键词 X 而触发"，便于追责 |

### 2.2 触发规则（**规则集 v1**）

| 规则 | 类型 | 命中条件 | 动作 |
|---|---|---|---|
| **T-1** | 关键词命中 | 诊断结论或建议中出现下列任一关键词（大小写不敏感）：<br>`停机`、`紧急`、`立即停止`、`人身安全`、`触电`、`泄漏`、`爆炸`、`火灾`、`超压`、`超温`、`拆除`、`带压作业`、`高温作业` | **强制审核** |
| **T-2** | 风险等级阈值 | 诊断输出的 `risk_level ∈ {high, critical}` | **强制审核** |
| **T-3** | 低置信度 | 复合置信度 `confidence < 0.60`（V5.0 §6.1；`0.75` 为自动生成线，`0.60` 为强制审核线） | **强制审核** |
| **T-4** | 证据不足 | 结论**缺少来源引用**（违反"无来源不出结论"），或 `graph_support` 无路径且检索得分低于阈值 | **强制审核**（同时标记为"证据不足"） |
| **T-5** | 职责分离强制 | 报告**提交者本人**发起审核 → 不允许自审（V5.0 §7.2） | **拒绝自审**，转派其他审核人 |
| **T-6** | 写操作前置 | 即将执行 `generate_report`（**写操作**） | **必经审核**（图外写库的前置条件） |

### 2.3 关键词表的维护纪律

| 项 | 规定 |
|---|---|
| 存放位置 | 规则集配置文件（P1 落 `configs/review-rules.yaml`；本阶段可硬编码在 `scripts/run_v5.py`） |
| 变更流程 | 新增/删除关键词须**走变更记录**（记入本文件版本历史），禁止随手改 |
| 大小写/全半角 | 统一预处理：转小写 + 全角转半角 + 去除空格干扰 |
| 命中判定 | **子串匹配**（不用正则，避免误伤）；如遇"不停机"这类反义，另设**否定词白名单**（如 `不停机检查` 不触发 T-1） |
| 人工抽检 | 每轮迭代抽检 ≥20 条结论，核对"该触发的触发了、不该触发的没触发"（误报/漏报各单独统计） |

## 三、审核状态机

### 3.1 状态定义

| 状态 | 英文标识 | 含义 | 是否终态 |
|---|---|---|---|
| **待审核** | `PENDING_REVIEW` | 已触发审核，等待审核人领取 | 否 |
| **审核中** | `IN_REVIEW` | 已被某审核人领取（持有 `lock:review:{thread_id}`） | 否 |
| **已通过** | `APPROVED` | 审核通过 | **是** |
| **已驳回** | `REJECTED` | 审核驳回（可附意见） | **是** |
| **超时** | `TIMED_OUT` | 超时未审，已执行降级动作（见 §四） | 否（转"待人工确认"） |
| **待人工确认** | `PENDING_MANUAL_CONFIRM` | 超时降级后的状态：流程**不挂起**，报告标注"初步判断"，仍可后续补审 | **是**（就流程而言） |

### 3.2 状态转移图

```
                    ┌──────────────────────────────────┐
                    │  触发（T-1 ~ T-6 任一命中）        │
                    └───────────────┬──────────────────┘
                                    ↓
                        ┌───────────────────────┐
                        │  PENDING_REVIEW 待审核 │
                        └───┬───────────────┬───┘
                            │               │
              审核人领取     │               │  4h 未审 → 通知备用审核人（状态不变）
              (SETNX 锁)    ↓               │
                        ┌───────────────────────┐
                        │   IN_REVIEW 审核中     │
                        └───┬───────┬───────┬───┘
                            │       │       │
                     通过   │       │ 驳回  │ 24h 未决 → TIMED_OUT
                            ↓       ↓       ↓
                  ┌──────────┐ ┌──────────┐ ┌──────────────────────────────┐
                  │ APPROVED │ │ REJECTED │ │ TIMED_OUT → PENDING_MANUAL_  │
                  │  已通过   │ │  已驳回   │ │ CONFIRM（流程不挂起，不写正式  │
                  └────┬─────┘ └────┬─────┘ │ 报告；标注"初步判断"）          │
                       │            │       └──────────────┬───────────────┘
                       ↓            ↓                      ↓
              [图外] generate_report                 人工补审（任意时刻）
              （幂等键去重，落库）                          ↓
                       ↓                            补审通过 → 正式报告
                  审计日志追加                             补审驳回 → 关闭
```

### 3.3 终态后的动作

| 终态 | 动作 |
|---|---|
| `APPROVED` | ① 图外执行 `generate_report`（带 `idempotency_key`）；② 报告落 PG 与审核记录；③ **归档 checkpoint**（见 `docs/checkpoint-decision.md` §七）；④ 审计日志追加；⑤ 释放 `lock:review:{thread_id}` |
| `REJECTED` | ① **不生成正式报告**；② 记录驳回意见（必填）；③ 归档 checkpoint；④ 审计追加；⑤ 若是"证据不足"导致，触发重新检索或人工补充 |
| `PENDING_MANUAL_CONFIRM` | ① **不写正式报告**；② 输出带"**初步判断**"标注的降级结论（Must #12）；③ 流程**不挂起**（不占用 checkpoint 热数据，可归档）；④ 保留补审入口 |

## 四、超时策略（**不设 TTL，但如何避免僵尸审核**）

### 4.1 核心矛盾与解法

| 矛盾 | 解法 |
|---|---|
| checkpoint **不设 TTL**（否则丢状态）→ 但没有任何超时机制就会产生**永久僵尸审核**（状态永远停在 `PENDING_REVIEW`，占用资源、无人处理） | **用"状态推进"代替"数据过期"**：数据永不删（无 TTL），但**状态机会超时并自动推进**到 `PENDING_MANUAL_CONFIRM`，流程不挂起 |

> **一句话**：**数据不老化，状态会老化。**

### 4.2 超时时间表（对齐 V5.0 §6.4）

| 时限 | 动作 | 状态变化 | 通知对象 |
|---|---|---|---|
| **T+0** | 触发审核，状态置 `PENDING_REVIEW` | — | ① 前端 `review:required` 事件推送；② 通知**主审核人** |
| **T+4h** 未审 | **通知备用审核人** | 状态**不变**（仍 `PENDING_REVIEW`） | 备用审核人（升级通知） |
| **T+24h** 未决 | **自动降级**：置 `TIMED_OUT` → `PENDING_MANUAL_CONFIRM`；**流程不挂起**；输出标注"初步判断"的降级结论 | `TIMED_OUT` → `PENDING_MANUAL_CONFIRM` | 主审核人 + 备用审核人 + 系统管理员 |
| **T+任意时刻** | 人工可**补审**（将 `PENDING_MANUAL_CONFIRM` 拉回审核流程） | `PENDING_MANUAL_CONFIRM` → `IN_REVIEW` | — |

### 4.3 避免僵尸审核的四条机制

| # | 机制 | 说明 |
|---|---|---|
| 1 | **状态老化扫描** | 后台定时任务（建议每 10min）扫描 `PENDING_REVIEW` / `IN_REVIEW` 且超过时限的记录，**主动推进状态**。**不依赖审核人操作** |
| 2 | **时间戳落库** | 每次状态变更写入 `entered_at`（进入该状态的时间）作为超时判定依据；超时计算**不依赖内存**，重启后依然可算 |
| 3 | **流程不挂起原则** | 超时后**强制输出降级结论**（标注"初步判断"），**绝不**让诊断流程无限等待。审核从"阻塞关卡"变为"质量提升环节" |
| 4 | **僵尸清单日报** | 每日输出"超过 24h 未闭环的审核记录"清单，作为运营指标（防止问题被静默堆积） |

### 4.4 为什么不用 Redis TTL 做超时

| 为什么不用 | 说明 |
|---|---|
| TTL 会**删数据**，而超时只想**改状态** | TTL 到期后 checkpoint 消失，"补审"就再也无法进行 → 与"人工补审入口"冲突 |
| TTL 到期是**静默**的 | 无法记录"为什么超时"、无法审计 |
| `noeviction` 与"部分 key 设 TTL"并存会造成认知混乱 | 见 `docs/checkpoint-decision.md` §3.3 的副作用声明 |

> **结论**：超时**只在应用层用时间戳判定**，Redis 侧对 checkpoint **一律不设 TTL**。

## 五、双审核人并发 resume 的处理策略

### 5.1 并发场景

| 场景 | 现象 | 风险 |
|---|---|---|
| S1 | 两个审核人**同时**点"通过" | 两次 resume → 两次 `generate_report` → **重复报告** |
| S2 | 审核人 A 点通过的同时，B 点驳回 | 状态冲突，结果不确定 |
| S3 | 同一审核人在两个浏览器标签页操作 | 同 S1 |
| S4 | 网络重试导致同一请求到达两次 | 同 S1 |
| S5 | 超时降级与人工审核**同时**发生 | 状态竞争 |

### 5.2 处理策略（三层防护）

#### 第一层：分布式锁（`lock:review:{thread_id}`，SETNX）

```
审核动作执行前：
  SET lock:review:{thread_id} <reviewer_id> NX PX 30000
  ├─ 成功  → 获得锁，执行审核动作
  └─ 失败  → 说明他人正在处理 → 返回"该报告正由 <reviewer> 处理中"，不执行
执行完成后：
  DEL lock:review:{thread_id}   （仅当锁的 value == 自己的 reviewer_id，用 Lua 脚本保证原子）
```

| 参数 | 值 | 理由 |
|---|---|---|
| 锁 key | `lock:review:{thread_id}` | 一报告一把锁 |
| 锁值 | `reviewer_id` | 保证"只删自己的锁"，避免误删他人锁 |
| 过期时间 | **30s**（`PX 30000`） | 防止审核人异常退出导致**死锁**；30s 足够覆盖审核动作（写库 + 释放锁） |
| 获取方式 | `SET ... NX PX` | 原子操作，避免 `SETNX + EXPIRE` 两步竞态 |

#### 第二层：数据库唯一约束（**最终防线，不依赖锁**）

```sql
-- PostgreSQL 唯一索引：一个 thread 只能有一份"正式报告"
CREATE UNIQUE INDEX uq_report_idem ON diagnosis_report(idempotency_key);
-- 且：一个 thread 只能有一个"终态审核记录"
CREATE UNIQUE INDEX uq_review_terminal
    ON review_record(thread_id)
    WHERE status IN ('APPROVED', 'REJECTED');
```

| 为什么必须有第二层 | 说明 |
|---|---|
| 锁可能失效 | 锁超时（>30s 的网络卡顿）、Redis 重启、多实例场景下锁语义弱化 |
| 唯一索引是**强一致**的 | 由数据库保证，**任何**并发路径都拦得住 |
| 做法 | `INSERT ... ON CONFLICT DO NOTHING RETURNING id` → 无返回 = 已存在终态 → 当前审核动作**被判定为重复**，返回已有结果，**不报错**，并记录一条"并发重复提交"审计 |

#### 第三层：状态前置校验（乐观并发）

```
执行审核动作前，校验：
  SELECT status, version FROM review_record WHERE thread_id = ?
  ├─ status 已是终态（APPROVED/REJECTED） → 拒绝，返回已有终态
  └─ status 为 PENDING_REVIEW/IN_REVIEW    → 继续，带 version 做 CAS 更新
UPDATE review_record SET status = ?, version = version + 1
  WHERE thread_id = ? AND version = ?      ← 版本不符则更新 0 行 → 判定为并发冲突
```

### 5.3 S1–S5 逐场景预期行为

| 场景 | 预期结果 | 靠哪一层 |
|---|---|---|
| S1 双通过 | 一次成功；另一次返回"已通过，report_id=X" | 第一层（通常）+ 第二层（兜底） |
| S2 通过 vs 驳回 | **先到者生效**；后者返回"已被 <reviewer> 处理为 <终态>" | 第二层 + 第三层 |
| S3 同人多标签 | 同 S1 | 第一层 |
| S4 网络重试 | **幂等返回同一结果**，不产生第二份报告 | 第二层（`idempotency_key`） |
| S5 超时 vs 人工 | **人工审核优先**：若人工审核在超时动作前完成，超时任务检测到终态即**跳过**；若超时已生效（`PENDING_MANUAL_CONFIRM`），人工补审**允许拉回**并覆盖降级结论（原降级结论保留在审计中） | 第三层 + 状态机 |

### 5.4 实测验证要求（T5.5，待 D7 填入）

| 验证项 | 方法 | 预期 | 实测 |
|---|---|---|---|
| 双审核人并发 resume | 脚本并发触发 2 次审核 | 仅 1 份报告 | 🔲 待 D7 填入 |
| 抢锁失败行为 | 持锁期间发第二次请求 | 明确提示"处理中"，无副作用 | 🔲 待 D7 填入 |
| 锁超时后二次提交 | 持锁 >30s 后第二次提交 | 由唯一索引拦住，仅 1 份报告 | 🔲 待 D7 填入 |
| 多 worker 行为 | 起 2 个 worker 消费同一 thread | 无重复副作用 | 🔲 待 D7 填入 |

## 六、审核记录留存与归档

| 项 | 策略 |
|---|---|
| **权威存储** | **PostgreSQL 为唯一权威源**（V5.0 §6.3）。审核记录、报告、审计日志均在 PG |
| **留痕范围** | 每次状态变更**追加一行**（不 UPDATE 历史行），形成完整时间线 |
| **不可篡改** | 审计专用表采用**追加表 + 触发器禁止 UPDATE/DELETE**（V5.0 §7.1） |
| **checkpoint 归档** | 审核达终态后，该 `thread_id` 的 checkpoint **移出 Redis 热数据**（导出 JSON 归档），Redis 只保留最近 N 个版本 |
| **保留期限** | 审核记录与报告：**长期保留**（工业诊断结论需可追溯）；checkpoint 归档文件：按项目保留策略（默认 ≥1 年，待定） |
| **归档可回放** | 归档的 checkpoint 必须能**重新加载用于补审**（验证方式：从归档恢复后能读到原状态） |
| **禁止** | ❌ 用 Redis 作为审核记录的唯一存储；❌ 归档时删除而不保留 |

## 七、审核动作的审计字段

每次审核动作（含状态变更、通知、超时推进）必须记录：

| 字段 | 类型 | 说明 | 必填 |
|---|---|---|---|
| `audit_id` | UUID | 审计行唯一标识 | ✅ |
| `ts` | timestamp(ms) | 动作发生时间（服务器时间） | ✅ |
| `thread_id` | string | 诊断流程 ID | ✅ |
| `report_id` | string | 关联报告 ID（若已生成） | ⭕ 可空 |
| `action` | enum | `TRIGGER` / `CLAIM` / `APPROVE` / `REJECT` / `TIMEOUT_NOTIFY` / `TIMEOUT_DEGRADE` / `RECLAIM` / `DUPLICATE_SUBMIT` | ✅ |
| `from_status` | enum | 变更前状态 | ✅ |
| `to_status` | enum | 变更后状态 | ✅ |
| `actor_id` | string | 操作人（审核人/系统）；系统动作用 `SYSTEM` | ✅ |
| `actor_role` | enum | `engineer` / `reviewer` / `kb_admin` / `sysadmin` / `SYSTEM` | ✅ |
| `trigger_rule` | string | 触发的规则编号（`T-1`~`T-6`），并记录**命中的关键词原文** | ⭕ 触发时必填 |
| `comment` | text | 审核意见（**驳回时必填**） | ⭕ |
| `idempotency_key` | string | 写操作幂等键（`generate_report` 相关动作必填） | ⭕ |
| `lock_acquired` | bool | 是否成功获得并发锁 | ✅ |
| `result` | enum | `SUCCESS` / `REJECTED_BY_LOCK` / `REJECTED_BY_UNIQUE` / `REJECTED_BY_CAS` / `ERROR` | ✅ |
| `error_detail` | text | 失败详情 | ⭕ |
| `client_ip` | string | 客户端 IP（审计溯源） | ✅ |
| `trace_id` | string | 全链路追踪 ID（与 API/Socket.IO 一致） | ✅ |
| `schema_version` | string | 审计 Schema 版本（如 `audit_v1`） | ✅ |

> **审计纪律**：`result` 为 `REJECTED_BY_LOCK` / `REJECTED_BY_UNIQUE` / `REJECTED_BY_CAS` 的记录**必须保留**——它们是"并发防护生效"的证据，不是噪音。

## 八、"审核不可恢复"风险的应对与降级路径

> 对应风险 **R11**（checkpoint TTL/驱逐丢状态）、**R12**（恢复后重复副作用）、**R-M5**（checkpoint 第三方实现），详见 `docs/risk-register.md` 与 `docs/known-issues.md`。

### 8.1 风险拆解与防线

| 子风险 | 后果 | 防线 |
|---|---|---|
| **状态被驱逐/过期** | 审核白做，流程丢失 | ① 实例级 `noeviction`；② checkpoint **不设 TTL**；③ 内存上限告警；④ 写失败显式报错不静默 |
| **进程/容器重启** | 内存状态丢失 | ① `appendonly yes`；② 重启恢复验证（T5.3） |
| **恢复后重复执行** | 重复报告 | ① `generate_report` **移出图内**；② `idempotency_key` + PG 唯一索引；③ 状态前置校验 |
| **第三方实现缺陷** | 不可预期的状态异常 | ① D6 定向复现（T5.2）；② 阻塞缺陷 → 切 PostgreSQL checkpointer（`docs/checkpoint-decision.md` §五） |
| **审核记录本身丢失** | 无法追溯责任 | ① PG 为唯一权威源；② 追加表 + 禁止 UPDATE/DELETE；③ Redis 不作为审核记录存储 |

### 8.2 降级路径（**分三级**）

| 级别 | 触发条件 | 降级动作 | 代价标注 |
|---|---|---|---|
| **L1 应用层规避** | 非阻塞缺陷（恢复慢、体积增长快等） | ① 归档策略加强；② 恢复耗时纳入性能预算；③ 缺陷登记为"可规避" | 对 `P95` 的影响（恢复耗时），须实测填入 |
| **L2 存储层降级** | 阻塞缺陷（B1–B7 任一） | 切 **PostgreSQL checkpointer**；重跑 T5.1–T5.7 | ① 对 `P95` 的影响（恢复耗时上升，须实测）；② 运维复杂度上升；③ **对 `Recall@5` 无影响**（须显式写明以闭环"降级必带代价"） |
| **L3 流程形态降级** | checkpoint 方案整体不可用 | 退到**无 checkpoint 的同步审核**：诊断完成后**同步等待**审核，不跨天、不重启。**审核窗口缩短为单次会话内** | ① 失去"跨天审核"能力（V5.0 §6.4 的 24h 策略失效）；② 可用性下降；③ **对 `Recall@5` 无影响** |

### 8.3 降级纪律（**硬性**）

> **降级必带代价**：任何降级都必须在报告与本文档中显式标注对 **`Recall@5`** 与 **`P95`** 的影响。
> 若确实无影响，也必须**写出"无影响"并说明理由**，不得留空。
> 违反即视为违反 Phase 0 三条铁律之三。

### 8.4 兜底保证（无论哪一级降级都成立的底线）

| 底线 | 说明 |
|---|---|
| 高风险 100% 有人签字 | 若技术方案失效，退到 L3 也**必须**保留人工审核这一关卡（安全边界不可让步） |
| 不重复写报告 | 幂等键 + 唯一索引是**最后防线**，在任何降级路径中都必须保留 |
| 全操作可审计 | 审计表为追加表，任何降级都不得取消审计 |
